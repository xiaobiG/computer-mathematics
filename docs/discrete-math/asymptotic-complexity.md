# 渐进复杂度：算法规模如何影响时间

## 学习目标

读完后，你能用量词写出 $O/\Omega/\Theta$ 的含义；从代码计数得到线性、二次和指数增长；证明有序数组双指针的线性上界；并区分增长率、常数成本和实测运行时间。

## 先问一个问题

一个程序在你的电脑上很快，不表示它面对十倍或百万倍数据仍然可用。复杂度研究输入规模 $n$ 变大时，资源消耗的增长率。

## 严格定义：不是“差不多快”

对足够大的 $n$，若存在常数 $c>0,n_0$，使 $0\le T(n)\le cf(n)$，则 $T(n)=O(f(n))$。$\Omega$ 将不等号反向；同时成立才是 $\Theta(f(n))$。例如对 $n\ge10$，$3n^2+10n\le4n^2$，又有 $3n^2+10n\ge3n^2$，故它为 $\Theta(n^2)$。

忽略常数和低阶项不是说它们不重要，而是在大规模下先抓住决定性的增长趋势。例如 $3n^2+10n$ 是 $\Theta(n^2)$。

## 常见增长率

| 复杂度 | 典型例子 |
| --- | --- |
| $O(1)$ | 数组按索引读取 |
| $O(\log n)$ | 二分查找 |
| $O(n)$ | 扫描数组 |
| $O(n\log n)$ | 归并排序 |
| $O(n^2)$ | 两层全量配对 |
| $O(2^n)$ | 枚举全部子集 |

## 算法实验：先计操作，再谈阶数

```python
from projects.algorithm_lab.complexity_counts import operation_counts, two_sum_sorted_trace

assert operation_counts(4) == {
    "linear_scan": 4, "all_unordered_pairs": 6, "all_subsets": 16,
}

pair, comparisons = two_sum_sorted_trace([1, 3, 4, 7, 11, 18], target=15)
assert pair == (2, 4)
assert comparisons <= 5
```

运行 `python -m unittest projects.algorithm_lab.test_complexity_counts`。`operation_counts` 用精确公式展示规模从 4 翻倍到 8 时：线性扫描翻倍、子集枚举增至 16 倍；全对枚举为 $n(n-1)/2$，趋近四倍。它不是性能基准，而是防止把单次计时误当增长率的可复核模型。

## 双指针为何只有线性次数

有序数组中，若 `values[left] + values[right] < target`，任何以当前 `left` 为左端的更小右端只会更小，因此 `left` 可安全右移；和过大时同理右移 `right`。这个不变量既证明不会错过可行对，也说明每次失败比较至少让一个指针向内移动。两指针总移动不超过 $n-1$ 次，所以即使代码有一个 `while` 和两种分支，比较次数仍是 $O(n)$，而不是 $O(n^2)$。

## 复杂度、内存与工程边界

时间复杂度必须说明操作模型：数组随机访问、哈希查询、整数位宽、缓存和 I/O 都会改变常数甚至基本操作的成本。空间也独立计量；归并排序常为 $O(n)$ 辅助空间，递归深度为 $O(\log n)$。复杂度不衡量网络延迟、数据倾斜、并行同步、垃圾回收或安全性。

主定理只适用于特定等分递推；不规则递归应使用[递推关系](/discrete-math/recurrences)、递归树或摊还分析。对小输入，常数和实现细节可能反转实际快慢；只有增长率不能替代基准测试。

## 常见误区

- **“两层代码就是 $O(n^2)$。”** 双指针、滑动窗口和摊还结构可能让内层总次数受线性限制。
- **“$O(n)$ 比 $O(n\log n)$ 在任何输入都快。”** 常数、内存分配和硬件会影响有限规模的实际时间。
- **“$O$ 是精确运行次数。”** 它是上界类别；要比较实现，还需操作计数和基准环境。
- **“复杂度解决所有性能问题。”** I/O、缓存未命中、锁竞争和数据布局也可能主导。

## 练习

1. **基础**：用定义证明 $7n+3$ 是 $O(n)$，给出一个可用的 $c,n_0$。
2. **推导**：证明两个指针合计最多移动 $n-1$ 次，并由此给出双指针查找的正确性和复杂度论证。
3. **编码**：为 `operation_counts` 增加三重循环的 $n^3$ 计数，并比较 $n=4,8$ 时的增长倍数。
4. **开放**：为一个实际服务分别列出 CPU、内存、网络和数据库成本；说明为何单写一个 Big-O 仍不足以制定容量计划。

## 练习答案提示

1. 例如取 $c=10,n_0=1$；当 $n\ge1$ 时 $7n+3\le7n+3n=10n$。写出“对所有 $n\ge n_0$”比只代几个输入更关键。
2. 给每根指针规定单调移动方向，并把每一次循环归因于其中一根指针的前进；它们都不能越过边界，因此总移动数有线性上界。正确性还须说明发现目标或两指针交错时为何可以停止。
3. 三重循环若每层都遍历 $n$ 次，计数应为 $n^3$；从 $4$ 到 $8$ 的理论倍数是 $8$，再区分操作数增长和真实运行时间的差别。
4. 分开估算请求 CPU 时间、驻留内存、网络字节和数据库查询/扫描量，并补充峰值并发与尾延迟；Big-O 不描述常数、I/O 等待、缓存和资源上限。
