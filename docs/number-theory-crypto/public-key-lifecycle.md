# 公钥身份与密钥生命周期：验签前还要验证什么

## 学习目标

你将能区分“签名在某公钥下有效”与“该公钥属于预期发布者”；写出密钥标识、用途、有效期、轮换和撤销的验证顺序；解释上下文绑定为何阻止跨协议误用；并说明这些协议状态不能由裸 RSA 等式替代。

## 从“验签通过”开始

若攻击者把自己的公钥连同自己的有效签名一起交给客户端，数学验签完全可能通过，但客户端并没有验证它期待的发布者。公钥需要可信的身份绑定：例如预置指纹、受信任证书链、透明日志或带外确认。签名等式只回答“此私钥是否产生了该签名”，不回答“这把公钥是谁的”。

## 直觉与定义：密钥是有状态的协议对象

一个可验证发布记录至少应绑定：

$$R=(\text{issuer},\text{key\_id},\text{algorithm},\text{purpose},\text{not\_before},\text{not\_after},\text{status},\text{context},\text{payload}).$$

其中 `key_id` 是查找线索，不是身份本身；`status` 可为 active、retired 或 revoked；`context` 把签名限定在“软件更新 v1”等协议语义中。验签应先确认身份链、算法和用途，再检查时间与撤销状态，最后在精确上下文和载荷上调用成熟库验签。

## 可运行审计清单

```text
1. 以固定信任锚或受信任证书链解析 issuer -> public key
2. 检查 algorithm 与 purpose 是否是本协议允许的组合
3. 检查 key_id 对应公钥、当前时间在有效期内，且状态不是 revoked
4. 将 context 与 payload 按协议规范编码，调用成熟库验签
5. 记录验证的 key_id、信任锚版本、撤销信息版本和结果
```

这里故意没有自制“证书格式”或签名代码。生产系统应使用经审计的 TLS/证书、签名库和撤销机制；教学玩具箱只可演示数学等式，不能承担身份基础设施。

不过，“候选记录不能自称可信”可以在不触碰真实密钥的前提下写成可审计的元数据约束。[已签名更新与防回滚](/number-theory-crypto/signed-release-anti-rollback)中的固定教学登记表按 `(issuer, key_id)` 查找声明的算法、用途和状态；候选包只能提出这些字段，不能携带一个 `key_identity_trusted=True` 来替代登记。该报告不会验签或建立现实身份，但它让生命周期顺序中的“先解析可信绑定”成为可重放输入，而不是一句未检验的清单。

可以运行现有玩具箱的签名等式测试，作为这条边界的对照：它只能证明教学实现的验签关系，并不会建立发布者身份、用途或撤销状态。

```bash
python -m unittest projects.crypto_toybox.test_signatures
```

## 正确性与边界

若第 1–3 步成立，验签公钥被绑定到预期身份、用途和有效状态；第 4 步再证明该身份对应的私钥认可了精确编码后的消息。任一步失败都应拒绝，而不是“只要数学验签成功就继续”。轮换时，新旧密钥可在预先定义的重叠期共存；撤销优先于有效期，避免已泄露私钥在形式上尚未到期时仍被接受。

这不是关于真实世界身份的数学证明：信任锚、证书颁发、撤销分发、时钟、日志可用性和客户端更新本身都有威胁模型。更不能把 `key_id`、显示名称或可下载的公钥当成身份认证。

## 失败案例与工程边界

- **公钥替换。** 只从消息中读取公钥会允许攻击者附带自己的有效签名。
- **上下文缺失。** 同一签名格式可能在“测试批准”和“生产发布”之间被重放。
- **只看有效期。** 已撤销密钥即使仍在时间范围内也不应接受。
- **硬编码永不过期密钥。** 轮换和泄露响应会变得不可操作。
- **自制撤销或填充。** 这些是协议和实现安全问题，应使用成熟标准与库。

## 常见误区

- **“key_id 就是身份。”** 它只是索引；身份来自可信绑定。
- **“签名能防止旧版本回滚。”** 不能；还需要版本策略和受保护的本地状态。
- **“轮换就是换一把密钥。”** 还包括分发、重叠期、记录和旧密钥处置。
- **“撤销列表下载失败就接受。”** 是否 fail-open 必须是显式风险决策，不能默默降级。

## 练习

1. 列出客户端接受软件更新前必须检查的五项状态。
2. 说明为何 `purpose=code-signing` 的公钥不应直接用于 TLS 身份。
3. 设计新旧密钥重叠期的验证规则，并说明撤销优先级。
4. 解释为什么数学验签不能单独防回滚。

## 练习答案提示

1. 信任锚/身份链、算法与用途、有效期、撤销状态、上下文与载荷验签。
2. 用途约束和上下文绑定减少跨协议误用；同一密钥材料不应被任意复用。
3. 两把已授权且未撤销密钥在明确窗口内可验；任何 revoked 状态立即拒绝。
4. 旧版本也可有有效签名；需保存最小版本或使用单调版本策略。
